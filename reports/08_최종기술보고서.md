# 콩잎 질병 분류 Vision AI API 서비스 기술보고서

## 1. 프로젝트 정보

- 프로젝트: ResNet18 기반 Beans 3클래스 분류와 동기·비동기 서빙
- 입력: JPG / PNG / WEBP 이미지 (5MB 이하, 1200만 픽셀 이하)
- 출력: `angular_leaf_spot` / `bean_rust` / `healthy`와 각 점수

  - Windows 11 + WSL2 Ubuntu 26.04
  - FastAPI와 Celery Worker는 `.venv`에서 실행 (Python 3.14.4)
  - Redis와 PostgreSQL은 Docker Compose로 실행
- 작성일: 2026-11-04

## 3. 아키텍처 및 데이터 흐름

- 동기: Browser → FastAPI → Redis Cache (DB 1) → (MISS면) ResNet18 → JSON 응답
- 비동기: Browser → FastAPI → `media/jobs/` 저장 + PostgreSQL `image_jobs`(queued) → Redis Broker (DB 2) → Celery Worker → Cache / ResNet18 → PostgreSQL(done) → 상태 조회
- ResNet18은 FastAPI 프로세스와 Worker 프로세스에서 따로 로드된다. 첫 요청 시간 (최종 모델): FastAPI 2,125ms, Worker 2,256ms
- compose.yaml의 web·worker·trainer 서비스는 이번 실행에 쓰지 않았다.
- 근거 문서: [산출물 2](02_시스템_아키텍처.md)

## 4. API·DB 설계

- 핵심 API
  - 동기 분류: `POST /api/sync/classify/` → 200
  - 비동기 접수: `POST /api/async/classify/` → 202 + `job_id`
  - 상태 조회: `GET /api/async/jobs/{job_id}/`
  - 서버 상태: `GET /health`
- 오류 코드: 400 (잘못된 이미지), 413 (5MB 초과), 422 (필드·형식 오류), 404 (없는 작업), 503 (큐 등록 실패, 코드로만 확인)
- Swagger(`/docs`)에는 200/202와 422만 표시된다. 응답 모델과 오류 응답이 코드에 선언되지 않았기 때문이다. 산출물 3이 실제 응답으로 보완한다.
- DB
  - PostgreSQL `image_jobs` 1개 테이블, PK `id`, `status` 인덱스
  - 비동기 작업만 기록한다. 동기 요청은 행을 만들지 않는다 (최종 모델로 실행해 확인: 동기 16회, 비동기 11회 → 행 11개)
  - 이미지 원본은 DB가 아니라 `media/jobs/<uuid>.bin`에 저장한다.
- 근거 문서: [산출물 3](03_API_명세서.md) / [산출물 4](04_DB_구조_작업이력.md)

## 5. 실제 버튼 처리 검증

- 동기식: [동기 분류] 버튼 → 분류가 끝난 뒤 200 응답. 최종 모델 예: `bean_rust_test.0.jpg` → bean_rust 0.7914, 응답 21.1ms (기준선 A 화면 예: `angular_leaf_spot_test.3.jpg` → 0.5927, 45ms)
- 비동기식: [Celery 작업 등록] 버튼 → 202 + `job_id` → 1초 간격으로 상태 조회 → done
  - 최종 모델 예: job 16, 접수 29.5ms, Worker 첫 작업이라 DB 생성~완료 2.31초 (모델 로드 포함). 이후 작업은 약 29ms
  - 기준선 A 화면 예: job 14, 접수 29ms, 화면 표시 전체 1,043ms (Worker 처리 0.037초, 나머지는 1초 조회 간격)
- 동기와 비동기는 같은 함수(`classify_with_cache` → `classify_image_bytes` → `get_classifier`)와 같은 캐시 키를 쓴다.
- 근거 문서: [산출물 5](05_AI버튼_처리흐름.md)

## 9. 최종 판정 및 한계

**판정**
- 필수 기능: 충족
  - Head-only Fine-tuning 모델을 생성하고 서비스에 연결했다.
  - 동기·비동기 API, Redis 캐시, Celery 처리, PostgreSQL 기록이 실환경에서 동작함을 확인했다 (기준선 A 모델로 서비스할 때 측정).
  - 최종 모델로 교체한 뒤 같은 테스트를 다시 실행해 13개 항목 PASS를 확인했다 (`model_id` = `artifacts/beans_resnet18_bs16_ep6`).
- 모델 분류 품질
  - 최종 모델 C: Validation 0.8346, Test 0.8750, Macro F1 0.8752
  - 기준선 A (Val 0.7669, Test 0.7188)보다 높다.
  - Full Fine-tuning(Val 0.9549, 참고값)보다는 Validation이 낮다.

**한계**
- 모델
  - 최종 모델은 epoch 6에서도 Val이 오르는 중이었다. 최적 epoch는 확인하지 않았다.
  - bean_rust Recall이 0.7907로 가장 낮고, angular_leaf_spot과의 혼동이 8건이다.
- Test 사용: 같은 Test를 기준선 A와 최종 모델 C에 각각 1회, 모두 2회 사용했다. A의 결과를 본 뒤 추가 실험을 했기 때문에 C의 Test 점수에 낙관 편향이 있을 수 있다.
- 모델 식별: DB와 응답의 `model_id`는 경로만 기록한다. 같은 경로의 모델 파일이 바뀌어도 구분할 수 없다 (job 1, 2는 다른 시점의 모델로 처리됐지만 `model_id`가 같음).
- 실험 관리
  - Full 실험 1회를 Head-only와 같은 출력 경로로 실행해서 Full 산출물이 남지 않았다.
  - Full 수치는 로그 기준 참고값이다.
- 성능 측정
  - 5회 반복, 같은 PC, 동시 부하 미측정
  - 비동기 최종 확인 시간은 50ms 조회 간격 단위로만 구분된다.
- 미실시 테스트: Worker 정지, Redis 중지(503)는 모의 테스트로만 확인했다.
- 데이터: 원본 출처와 분할 방법은 제공된 `dataset/` 구성을 그대로 따랐다. 현장 조명·촬영 조건 차이는 평가하지 않았다.

**추후 과제**
- 다음 실험부터는 하이퍼파라미터 후보를 먼저 정하고 Validation으로만 비교한 뒤, Test는 최종 모델에 1회만 사용
- epoch를 더 늘린 실험으로 최적 epoch 확인 (Validation 기준)
- 모델 파일 해시를 `model_id`나 별도 컬럼에 기록
- 8장의 `review_required` 규칙을 Validation 기준으로 실험
- 실험별 output 폴더 분리
